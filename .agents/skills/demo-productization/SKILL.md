# Demo Productization Skill

## 1. 目标

将已经完成本地开发和验证的 Demo，提炼为可跨企业、跨项目、跨环境复用的通用成品，并沉淀到 GitHub。

本 Skill 只负责产品化提炼与发布，不负责重新研发 Demo。

## 2. 核心标准

1. **先理解，再修改**：先检查项目目标、功能、架构、依赖、运行方式和实际测试情况，不得只看 README 就开始重构。
2. **保留已验证能力**：以实际运行成功的功能为基础，不随意改变核心功能和技术路线。
3. **真正通用化**：区分通用能力、企业专属内容、可配置内容和无效内容；不能只替换企业名称或测试数据。
4. **跨平台优先**：核心业务逻辑和数据处理尽量独立于单一智能体平台，避免不必要的平台锁定。
5. **适配层分离**：平台专属的 Agent、Skill、工具调用和配置方式应与核心能力分离。
6. **最小必要改造**：不预设技术架构、目录结构或开发语言；根据项目实际情况选择最简单、可靠的抽象方式，不为通用化而过度设计。
7. **真实验收**：实际运行和测试产品化后的成品；未验证的内容必须明确标记。

## 3. 主要兼容平台

长期兼容目标：

- OpenAI Codex
- Claude
- DeepSeek Harness
- 千问办公
- WorkBuddy
- Accio Work

不要求每个项目都开发六套独立版本。应优先保持核心能力平台无关，再根据项目功能和平台能力选择必要的适配方式。

适合时优先采用开放标准和通用接口（如 API、MCP、OpenAPI 等），但不得为了使用某项标准而增加不必要的复杂度。

## 4. 执行流程

### ① 项目审查

检查项目文件，弄清楚 Demo 的目标、功能、技术实现、外部依赖、运行方式、已验证结果和遗留问题。先形成完整理解，再开始改造。

### ② 通用化抽象

将项目内容分类处理：

- **通用能力**：保留并整理为可复用功能。
- **企业专属规则与参数**：在合理情况下配置化或剥离。
- **企业数据、凭证和敏感信息**：排除在通用成品及公开发布内容之外。
- **平台专属依赖**：判断能否改为通用接口，或独立放入平台适配层。
- **无效文件与开发残留**：确认无用后再清理。

### ③ 成品整理

进行最小必要的代码和文件整理，使成品尽量能够脱离原企业和原开发环境，独立配置、安装和使用。

保留必要文档，至少说明项目用途、核心功能、依赖、安装配置、运行方法和已知限制。根据项目需要补充平台接入说明。

### ④ 成品验收

实际检查：

- 核心功能是否完整，原有已验证能力是否退化。
- 是否仍依赖原 Demo 的企业数据、账号、路径或内部环境。
- 更换企业配置或数据后，通用能力是否仍可使用。
- 安装、配置和运行是否有明确说明。
- 是否存在缺失依赖、敏感信息、授权或发布风险。

对六个主要平台分别标记兼容状态：

- **已实际测试通过**
- **具备适配条件，尚未测试**
- **暂不支持 / 不适用**

不得把理论上可适配描述为已经兼容。没有必要的适配工作不应为了凑齐平台而强行开发。

### ⑤ GitHub 发布

检查发布内容，排除未经授权的企业资料、客户数据、凭证、密钥和无关文件；完善 README 和版本说明。

优先使用现有合适仓库，按其现有组织方式发布。完成提交和推送后，检查远程仓库，确认文件与提交记录正确。目标仓库或发布权限不明确时，先询问，不擅自发布。

## 5. 执行约束

- 不破坏原始 Demo；优先在独立副本或分支中完成产品化。
- 不擅自改变已验证的核心功能。
- 不预设所有项目必须使用相同架构、技术栈或目录结构。
- 不引入没有实际必要的技术组件。
- 不删除尚未确认无用的文件。
- 不上传未经授权的代码、企业资料、数据或凭证。
- 不以代码检查代替实际运行测试。
- 不隐瞒未完成事项，不虚报测试或发布结果。

## 6. 最终交付

完成后简要汇报：

1. **通用成品**：提炼出了什么能力，适用范围是什么。
2. **抽象改造**：保留、配置化、剥离和清理了哪些内容。
3. **测试结果**：实际测试内容、结果及未验证事项。
4. **平台兼容**：六个主要平台各自的兼容状态。
5. **交付位置**：本地成品路径、GitHub 仓库地址、版本和提交状态。

**最终原则：以已验证的 Demo 为基础，以最小必要改造，实现最大程度的跨企业、跨环境、跨智能体平台复用。**
